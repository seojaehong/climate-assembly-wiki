- **★ 설계 결정 세 가지 — 다시 논의하지 말 것.**
  1. **「현재 대표」를 따로 저장하지 않는다.** `representativeOf()` 가 append-only `history` 의
     마지막 사건에서 파생한다. 맞아야 하는 저장소를 둘 두면 언젠가 어긋나고, 어긋난 순간 화면이
     조용히 거짓을 보여준다(`four-category.ts` 가 「범주별 배열」을 버린 것과 같은 이유).
     이 「마지막 사건이 이긴다」는 US-007 읽기 RPC(`order by ... e.id desc`)와 **같은 규칙**이라
     나중에 서버에 붙여도 화면과 DB 의 해석이 하나다. 묶음 구성이 바뀌어 대표가 그 묶음에서
     빠지면 예전 지목을 되살리지 않고 null 을 낸다(이력은 남는다) — 읽기는 너그럽게, 쓰기는 엄격하게.
  2. **시각(`at`)을 actor 안에 넣었다.** AC 가 못 박은 네 인자 모양
     `pickRepresentative(state, groupId, noteId, actor)` 을 지키면서 **모듈이 시계를 읽지 않게**
     하려는 것이다(US-011 이 `takenAt` 인자로 요구하는 것과 같은 규칙). 「누가」와 「언제」는
     어차피 한 사건의 두 면이라 한 객체에 있는 게 자연스럽다. 테스트가 시각에 안 흔들린다.
  3. **금지는 검사가 아니라 API 모양으로 막았다.** ①모더레이터 단독은 `citizenConfirmed: true`
     없이는 예외 → 화면이 확인 단계를 건너뛰면 지목 자체가 성립하지 않는다. ②이 API 는 카드 **id 만**
     받는다 — 문장을 넣을 인자가 없으니 「새 문장을 대표로」가 불가능하다. ③`groups` 는 같은 참조로
     그대로 넘어간다 — 지목이 묶음의 카드를 건드릴 방법이 없다.
- **일부러 안 만든 것**(US-006 이 `countsByCategory` 를 US-008 에 넘긴 선례) —
  묶음을 만드는 함수(체크된 짝 → groups), `syncGroups`, 화면용 `representativeNoteIds`.
  전부 US-010 의 화면 요건이라 그 story 에서 필요한 모양대로 낸다.
