# 관련 의제 위키 카드 최종 기능계획

작성일: 2026-06-25  
문서 상태: v1 이후 최종 기능계획  
소유 범위: 문서 산출물, 코드 변경 없음

## 목적

현재 메인 구현 범위인 v1 로컬 정적 데이터 기반 "관련 의제 위키 카드"를 출발점으로 삼아, 이후 완성본에서 필요한 데이터, 검수, 추천, 공개, 운영 기능을 하나의 제품 계획으로 정리한다.

이 기능의 목표는 시민회의 진행자가 의제 간 맥락을 빠르게 파악하고, 발언과 제안이 어떤 쟁점, 근거, 우려, 조건과 연결되는지 확인하도록 돕는 것이다. 카드는 결론을 대신 내리는 장치가 아니라, 숙의 과정에서 놓치기 쉬운 관련 의제와 소수의견을 다시 보이게 하는 안내 표면이다.

## 운영 원칙

하버마스 원칙은 다음 문장으로 고정한다.

> AI가 합의를 만드는 것이 아니라 숙의를 돕고 소수의견을 보존/가시화한다.

이에 따라 시스템은 다음을 하지 않는다.

- AI가 최종 합의문을 자동 확정하지 않는다.
- 다수 의견에 맞지 않는 우려를 숨기거나 낮은 가치로 처리하지 않는다.
- 출처가 없는 추천을 권위 있는 판단처럼 표시하지 않는다.
- 관리자 검수 전 항목을 공개 카드나 발표 화면에 자동 반영하지 않는다.

시스템은 다음을 한다.

- 관련 의제, 근거, 조건, 우려, 가치 충돌을 구조화해 보여준다.
- 소수의견과 반대 근거를 별도 신호로 보존한다.
- 진행자가 추가 질문을 던질 수 있도록 검토 포인트를 제안한다.
- 공개 화면에는 검수된 데이터와 출처만 노출한다.

## 사용자와 화면

### 시민 공개 화면

- 관련 의제 카드: 현재 의제와 연결된 쟁점, 제안, 우려, 근거를 요약한다.
- 출처 표시: 원문, 회차, 자료명, 발언 또는 입력 식별자를 함께 제공한다.
- 공개 상태 배지: 검수 완료, 검수 중, 비공개, 출처 확인 필요를 구분한다.
- 모바일 우선 레이아웃: 작은 화면에서도 카드 제목, 관계 유형, 출처가 먼저 보이게 한다.

### 진행자 화면

- 의제별 관련 카드 묶음: 진행 중인 세션에서 바로 참조할 수 있게 한다.
- 추천 후보 큐: LLM이 제안한 연결, 요약, 질문을 검토한다.
- 소수의견 레일: 반복되지는 않지만 중요한 우려를 따로 모아 표시한다.
- 발표 모드 전환: 시민에게 보여줄 항목만 큰 글자와 간결한 관계선으로 표시한다.

### 관리자 화면

- 후보 승인, 수정, 병합, 반려.
- 공개/비공개 상태 변경.
- 출처 누락, 중복 의제, 오분류 수정.
- 감사 로그 확인과 롤백 후보 검토.

## 데이터 모델 계획

v1은 로컬 정적 데이터로 시작하되, 완성본은 Supabase를 기준 저장소로 둔다. DB 스키마 변경은 별도 migration 문서와 사용자 승인 후 진행한다.

핵심 엔티티:

- `agenda`: 원 의제, 제안, 질문, 쟁점의 기준 항목.
- `agenda_relation`: 관련 의제 간 관계. 예: supports, opposes, requiresCondition, hasConcern, hasEvidence, similarTo.
- `ontology_node`: Issue, Claim, Proposal, Concern, Condition, Value, Evidence 단위 노드.
- `ontology_edge`: 노드 간 의미 관계.
- `source_reference`: 원문 문서, 회의 자료, 발언, 입력 폼, 관리자 메모 출처.
- `review_queue_item`: LLM 또는 규칙 기반 후보.
- `review_action`: 승인, 수정, 병합, 반려, 공개 상태 변경 이력.
- `publication_gate`: 공개 가능 여부와 공개 범위.
- `audit_log`: 누가, 언제, 무엇을, 왜 바꿨는지 남기는 append-only 로그.

공개 읽기 경로는 raw table 직접 노출 대신 검수 완료 view 또는 RPC로 제한한다. 비공개 발언, 원문 전문, 검토 중 후보, 관리자 메모는 익명 클라이언트에서 접근할 수 없어야 한다.

## Supabase 연동

### 단계

- 로컬 정적 JSON 어댑터 유지: 현재 v1 안정성을 보존한다.
- Supabase read adapter 추가: 검수 완료된 의제와 관계만 읽는다.
- Supabase realtime 구독: 관리자 또는 진행자 화면에서 검수 완료 변경사항을 실시간 반영한다.
- static fallback 유지: DB 장애나 네트워크 실패 시 마지막 검수 스냅샷을 표시한다.

### 정책

- anon public read: 공개 승인된 카드와 관계만 허용.
- moderator read/write: 검토 큐, draft 그래프, 세션 내부 메모 접근.
- admin write: 공개 상태, 병합, 반려, 출처 보정, 롤백 승인.
- service role: LLM 추출 작업, batch import, snapshot export.

### 실패 처리

- Supabase 연결 실패 시 "읽기 전용 스냅샷" 상태를 표시한다.
- 쓰기 실패는 화면 알림과 로그를 남긴다.
- realtime 구독 끊김은 조용히 무시하지 않고 관리자 화면에 상태를 표시한다.

## LLM 추천과 검토 큐

LLM은 공개 데이터에 직접 쓰지 않고 후보만 만든다.

추천 유형:

- 현재 카드와 의미적으로 가까운 의제 후보.
- 같은 출처 또는 같은 세션에서 나온 관련 의제.
- 근거가 부족한 주장에 대한 추가 질문.
- 조건이 빠진 제안에 대한 검토 질문.
- 반복되지는 않지만 중요한 우려 또는 소수의견 후보.
- 중복 카드 병합 후보.

검토 큐 필드:

- 후보 유형.
- 후보 제목과 설명.
- 연결 대상 의제.
- 관계 유형.
- 사용된 출처 목록.
- LLM 실행 식별자와 프롬프트 버전.
- 관리자 검토 상태.
- 반려 또는 수정 사유.

검토 액션:

- 승인: 공개 가능 후보 또는 내부 draft로 이동.
- 수정 승인: 문구, 관계, 출처를 고쳐 반영.
- 병합: 기존 카드에 연결.
- 반려: 사유와 함께 보관.
- 보류: 출처 확인 또는 운영진 판단 대기.

## 실시간 온톨로지

실시간 온톨로지는 회의 중 새 입력이 들어올 때 의제 구조를 업데이트하는 내부 작업 표면이다. 공개 그래프가 아니라 진행자와 관리자 검수용 draft 계층으로 시작한다.

노드 유형:

- Issue: 다루는 쟁점.
- Claim: 사실 주장 또는 판단.
- Proposal: 실행 제안.
- Concern: 우려, 반대, 소수의견.
- Condition: 실행 조건.
- Value: 충돌하거나 강조되는 가치.
- Evidence: 자료, 경험, 사례, 수치가 포함된 근거.

관계 유형:

- supports: 뒷받침한다.
- opposes: 반대하거나 긴장을 만든다.
- hasConcern: 우려를 가진다.
- requiresCondition: 조건을 필요로 한다.
- hasEvidence: 근거를 가진다.
- modifies: 수정하거나 보완한다.
- isAbout: 특정 쟁점에 관한 것이다.

실시간 반영 원칙:

- 새 후보는 draft에만 들어간다.
- 관리자 검수 후 reviewed snapshot으로 승격한다.
- 발표 모드와 공개 페이지는 reviewed snapshot만 사용한다.
- 모든 노드와 관계는 출처 식별자를 가져야 한다. 관리자 작성 항목은 moderator-created로 표시한다.

## 관리자 검수

관리자는 의제 카드의 품질과 공개 가능성을 책임진다.

검수 기준:

- 출처가 존재하는가.
- 관계 유형이 과장되지 않았는가.
- 요약이 원문 의미를 왜곡하지 않는가.
- 소수의견이 삭제되거나 중립화되지 않았는가.
- 개인정보 또는 비공개 정보가 포함되지 않았는가.
- 공개 화면에 표시해도 회의 운영상 문제가 없는가.

검수 상태:

- proposed: 시스템 또는 LLM 후보.
- needs-source: 출처 확인 필요.
- needs-edit: 관리자 수정 필요.
- approved-internal: 내부 진행자 화면에서 사용 가능.
- approved-public: 공개 화면과 발표 모드 사용 가능.
- rejected: 반려.
- archived: 보관.

## 감사 로그

감사 로그는 append-only로 운영한다. 기존 로그를 수정하지 않고 새 이벤트를 추가한다.

기록 대상:

- 후보 생성.
- 관리자 승인, 수정, 반려.
- 공개/비공개 상태 변경.
- 카드 병합과 분리.
- 출처 추가 또는 삭제.
- 발표 스냅샷 생성.
- 권한 변경.
- batch import 또는 export 실행.

로그 필드:

- event_id.
- actor_id.
- actor_role.
- action_type.
- target_type.
- target_id.
- before_snapshot.
- after_snapshot.
- reason.
- created_at.

감사 로그는 운영자가 나중에 "왜 이 카드가 공개되었는지", "어떤 출처를 근거로 연결되었는지", "누가 반려했는지"를 재구성할 수 있어야 한다.

## 공개/비공개 게이트

공개 게이트는 데이터가 시민 화면, 발표 화면, 관리자 화면 중 어디까지 나갈 수 있는지 결정한다.

게이트 기준:

- 출처 검증 완료.
- 개인정보 제거.
- 관리자 승인.
- 회의 운영상 공개 가능.
- 소수의견 보존 여부 확인.
- 원문과 요약의 의미 일치 확인.

공개 범위:

- private-draft: LLM 후보와 내부 작업물.
- moderator-only: 진행자 검토와 회의 운영용.
- reviewed-private: 검수는 끝났지만 공개하지 않는 자료.
- public-card: 시민 공개 카드.
- presentation: 발표 모드에 노출 가능한 축약본.

출처가 없거나 비공개 입력에서 온 항목은 기본값을 private-draft로 둔다.

## 성능, 모바일, 발표 모드

### 성능

- 관련 카드 목록은 페이지 단위 또는 세션 단위로 지연 로딩한다.
- 관계 그래프는 카드 상세 진입 시 확장한다.
- Supabase 응답은 검수 완료 view 기준으로 최소 필드만 가져온다.
- 정적 fallback JSON은 빌드 또는 운영 스냅샷으로 생성한다.
- 오류와 응답 지연은 관리자 로그에 남긴다.

### 모바일

- 카드 제목, 관계 유형, 출처 상태를 첫 화면에 표시한다.
- 긴 설명은 접힘 영역으로 둔다.
- 관리 액션은 실수 방지를 위해 확인 단계를 둔다.
- 작은 화면에서는 그래프보다 카드 목록과 출처 링크를 우선한다.

### 발표 모드

- 공개 승인된 항목만 노출한다.
- 큰 글자, 높은 대비, 제한된 색상 체계를 사용한다.
- 진행자가 소수의견, 조건, 근거 누락을 빠르게 강조할 수 있어야 한다.
- 발표 스냅샷은 생성 시각과 출처 상태를 함께 기록한다.
- 발표 모드는 편집 기능을 제공하지 않는다.

## 데이터 품질과 출처 검증

품질 게이트:

- 모든 공개 카드에는 하나 이상의 출처가 있어야 한다.
- 출처가 문서인 경우 문서명, 페이지 또는 섹션, 추출 시각을 남긴다.
- 출처가 발언 또는 입력인 경우 세션, 테이블 또는 입력 식별자, 검수 상태를 남긴다.
- LLM 요약은 원문 링크 또는 원문 발췌 기준으로 검토한다.
- 중복 의제는 삭제보다 병합 이력 보존을 우선한다.
- 상충 의견은 하나의 결론으로 합치지 않고 관계로 표시한다.

데이터 품질 리포트:

- 출처 없는 카드 목록.
- 공개 대기 항목 목록.
- 반려 사유 분포.
- 중복 후보 목록.
- 소수의견으로 표시된 항목 목록.
- 최근 변경된 공개 카드 목록.

이 리포트는 운영 전 점검과 회의 후 회고에 사용한다.

## 운영 절차

### 회의 전

- 정적 의제 데이터와 기존 위키 카드 최신 상태를 확인한다.
- Supabase 연결, 권한, realtime 상태를 점검한다.
- 공개/비공개 기준과 개인정보 처리 기준을 운영진에게 공유한다.
- 발표 모드에 노출할 기본 카드 묶음을 사전 검수한다.
- fallback JSON 스냅샷을 생성한다.

### 회의 중

- 시민 입력 또는 진행자 메모를 수집한다.
- LLM 추천 후보는 검토 큐로만 보낸다.
- 진행자는 필요한 경우 관련 카드와 소수의견 레일을 참고해 질문한다.
- 관리자는 공개 가능한 후보만 승인한다.
- 발표 화면은 reviewed snapshot만 사용한다.

### 회의 후

- 새로 승인된 카드와 반려된 후보를 검토한다.
- 출처 누락 항목을 보정한다.
- 감사 로그와 변경 이력을 보관한다.
- 공개용 스냅샷과 내부 보관용 스냅샷을 분리한다.
- 데이터 품질 리포트를 docs 또는 evaluation 산출물로 남긴다.

## 구현 로드맵

### Phase A: v1 안정화

- 로컬 정적 데이터 기반 관련 의제 카드 완성.
- 카드 UI, 출처 표시, 빈 상태, 오류 상태 정리.
- 현재 데이터 구조를 Supabase 전환 가능한 shape로 문서화.

### Phase B: 검수 가능한 DB 기반

- Supabase read adapter 설계.
- 공개 view 또는 RPC 설계.
- review_queue, publication_gate, audit_log migration 초안 작성.
- 사용자 승인 후에만 migration 적용.

### Phase C: LLM 후보와 관리자 검수

- LLM 추천은 review_queue에만 저장.
- 관리자 승인, 수정, 병합, 반려 화면 구현.
- 출처 누락과 비공개 항목을 기본 차단.

### Phase D: 실시간 온톨로지와 발표 운영

- realtime draft ontology 도입.
- reviewed snapshot export.
- 발표 모드와 모바일 최적화.
- 운영 전 점검 리포트와 회의 후 품질 리포트 생성.

## 완료 기준

최종 완성본은 다음 조건을 만족해야 한다.

- 관련 의제 카드가 정적 fallback과 Supabase 검수 데이터를 모두 지원한다.
- LLM 추천은 검토 큐를 거치며 직접 공개되지 않는다.
- 실시간 온톨로지는 draft와 reviewed snapshot을 분리한다.
- 관리자 검수, 공개/비공개 게이트, 감사 로그가 연결된다.
- 공개 카드에는 출처와 검수 상태가 표시된다.
- 소수의견은 별도 신호로 보존되고 발표 모드에서 강조할 수 있다.
- 모바일 화면과 발표 화면에서 핵심 맥락을 빠르게 읽을 수 있다.
- 운영 전후 절차와 데이터 품질 리포트가 남는다.
