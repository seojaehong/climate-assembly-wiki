# 백업 — 무엇이 우리를 지키나

2026-08-30 점검 결과와 조치. **이 문서의 요지: 지금 우리를 지키는 것은 CI 가 아니라 로컬 백업이다.**

## 사실

| 항목 | 상태 |
|---|---|
| Supabase PITR | **없음.** 지워지면 되돌릴 수단이 백업본뿐 |
| 서버 스냅샷 마지막 | **2026-07-25** (8.29 행사 전체가 0회) |
| 8.29 당일 워크플로 | 05:09 UTC **실패**(exit 1). 11:39 는 창 밖이라 skip |
| 실패 알림 | **알림 스텝도 함께 실패**했다 — `curl: (2) no URL specified` |
| 등록된 시크릿 | Cloudflare 2개뿐. Supabase·Drive·Discord **전부 없음** |
| 8.29 를 실제로 지킨 것 | 로컬에서 돌린 `scripts/backup-0829.mjs` (스냅샷 17본) |

즉 「백업이 죽었다」가 아니라 **「백업이 죽은 것을 알릴 경로까지 죽어 있었다」** 가 정확한 기술이다.

## ★ 왜 CI 로 내용을 나르지 않는가

**이 저장소는 public 이다.** GitHub Actions 아티팩트는 공개 저장소에서 누구나 내려받을 수 있다.
조별 산출물에는 시민 발언과 이름이 들어 있다. **CI 에 내용을 실으면 그 자체가 유출이다.**

그래서 설계를 이렇게 나눈다.
- **내용 백업 = 로컬**(아래). OneDrive 가 오프사이트로 동기화한다
- **CI = 실패를 알리는 역할만**. 내용을 다루지 않는다

## 행사 당일 하는 일 — 딱 두 단계

1. `wiki\.env.backup` 을 만든다 (**gitignore 됨. 절대 커밋하지 말 것 — 공개 저장소다**)
   ```
   HQ_OPERATOR=이름
   HQ_PASSWORD=비번
   ```
2. `wiki\scripts\backup-watch.bat` 을 더블클릭하고 창을 열어 둔다

5분마다 백업하고, 내용이 같으면 새 파일을 만들지 않는다(체크섬 비교).
산출: `10_작업산출물\2026-08-29_산출물_백업\` + 항상 최신인 `latest.json`

수동으로 한 번만 돌리려면:
```bash
export PATH="$HOME/tools/node-v20.18.0-win-x64:$PATH"   # Node 20 필수
HQ_OPERATOR=이름 HQ_PASSWORD=비번 node scripts/backup-0829.mjs
```

## 2026-08-30 에 고친 것

- `backup-0829.mjs` 가 `HQ_OPERATOR`/`HQ_PASSWORD` **환경변수**를 받는다.
  예약 실행에 비번을 인자로 박으면 프로세스 목록에 노출되기 때문이다
- `backup-watch.bat` 신설 — 5분 간격 로컬 백업
- `snapshot.yml` **알림이 자기가 실패하던 것**을 고쳤다. 웹훅이 없으면
  `::error::` 로 로그에 크게 남기고 `exit 0` 한다. 조용히 죽지 않는다
- `snapshot.yml` **야간 공백**을 메웠다. 종전 `0-12 12 9` + `0-9 13 9` 는
  **9/12 22시 ~ 9/13 09시 KST 가 비어 있었다.** 합숙은 1박 2일인데 밤이 빠져 있었다.
  `*/5 * 12 9 *` 로 9/12 를 통째로 덮는다
- WebSocket 스텁으로 Node 20 에서 스크립트가 다시 돈다(별건, `scripts/lib/node-ws-shim.mjs`)

## 아직 남은 것

  등록해야 서버 스냅샷이 산다. **다만 위 로컬 경로가 있으면 없어도 데이터는 지켜진다**
