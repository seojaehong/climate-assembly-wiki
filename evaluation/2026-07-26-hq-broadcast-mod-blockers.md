## 1. 결론 (먼저 읽을 것)

**빌드는 통과했다. 그러나 배포 준비 완료가 아니다.** 이유 3가지:

1. **시각 검증이 한 건도 실시되지 않았다.** 브라우저 확장(claude-in-chrome)이 연결되지 않아
   실제 화면을 한 번도 보지 못했다. 아래 §5 체크리스트는 사람이 직접 확인해야 한다.
2. **★ 1080p 프로젝터에서는 송출 카드의 출석 숫자가 보이지 않는다.** (§4, 산술 근거 포함)
   현장 화면의 실제 해상도를 확정하기 전에는 US-003~006의 목적이 달성됐다고 말할 수 없다.
3. **이 브랜치에는 내 작업이 아닌 DB 마이그레이션이 섞여 있고, 타입체크는 그것을 검증하지 못한다.** (§6)

## 4. ★ 미해결 — 1080p에서 출석 숫자가 보이지 않는다

**증상**: 송출 카드 하단의 출석 '현재/전체'(라벨 28px + 숫자 64px)가 카드 아래로 잘려 렌더되지 않는다.

**원인 (산술)**: 송출 카드는 `flex flex-col` + `overflow-hidden`이고, 헤더와 참여 블록에만
`shrink-0`이 걸려 있다(US-004). 따라서 초과분은 **출석 블록 하나가 전부 흡수**한다.
출석이 보이는지는 총 내용 높이가 아니라 **잔여높이** 하나로 결정된다.

```
고정 소비 = 헤더 106(이름 50 + gap 8 + 배지 48) + gap 8 + 참여 112(라벨 20 + pb 4 + 숫자 88) + gap 8
          = 234px
트랙내부 = (뷰포트높이 H − 160 − 24) / 3 − 4(border) − 32(p-4)
출석 블록 소요 = pt-2 8 + 라벨 28 + 숫자 64 = 100px
```

| 해상도 | 트랙내부 | 잔여 | 결과 |
|---|---|---|---|
| 1440 x 900 | 203px | **음수** | 참여 88px 숫자만으로 이미 초과 |
| 1920 x 1080 | 262px | 28px | 100px 필요 → **72px 부족, 출석 안 보임** |
| H ≥ 약 1294px | — | ≥ 100px | 정상 렌더 |

즉 **88px 득표수(US-004) + 64px 출석(US-006) + 40px 조 이름 + 32px 배지를 5x3 그리드에
넣는 것은 1080p에서 산술적으로 불가능하다.**

**왜 AC 임계값을 낮춰서 통과시키지 않았나**: 낮추면 8~15m 판독이라는 이 프로젝트의 대전제를
잃는다. 숫자만 작아진 채 "통과"로 기록되면 현장에서 발견된다.

**필요한 행동 (사람)**:
1. **8/29 현장 대형 스크린의 실제 해상도를 확정할 것.** 이게 첫 번째 액션이다.
2. 1080p로 확정되면 다음 중 하나를 별도 story로 다뤄야 한다 —
   (a) `h-[calc(100vh-160px)]`(`src/islands/mod/HqGrid.tsx` 그리드 div)의 `160`을 줄여 트랙을 키운다.
       이 값은 헤더/푸터 실측이 아니라 **아직 눈으로 검증되지 않은 매직넘버**다.
   (b) 5x3 고정 그리드를 포기하고 2화면 롤링 등으로 바꾼다.
   (c) 송출 카드에서 출석 표기를 뺀다(참여 수치만 남긴다).
3. 1440p급 이상이면 그대로 두면 된다.

브라우저 확장이 연결되지 않아 **아래 항목은 한 건도 확인되지 않았다.**

### /hq 송출 모드 (파라미터 없음)
- [ ] 상태 요약 4버튼 · 분과 필터 칩 · '조 비교하기' · 출석 관리자 · 카드 하단 '상세 보기 →' ·
      상단 안내 문단이 **하나도 안 보이는지**. 연결 상태 배지와 '마지막 갱신 hh:mm:ss'는 보이는지.
- [ ] 페이지 로드 순간 조작 UI가 **한 프레임도 번쩍이지 않는지**(hydration 기본값 false 확인).
- [ ] 15조가 5열 x 3행으로 한 화면에 들어오고 **세로 스크롤바가 생기지 않는지**.
      스크롤바가 보이면 `h-[calc(100vh-160px)]`의 160을 키워야 한다.
- [ ] 조 이름 40px이 **오른쪽에서 잘리지 않는지**(내용 폭 여유가 37px뿐이다 — 조 이름이
      '1분과 1조'보다 길어지면 무성 클리핑이 난다).
- [ ] **88px 득표수가 세로로 눌리거나 밑이 잘려 보이면 즉시 보고** — 의도된 게 아니다(shrink-0 보호 파손).
- [ ] 카드 테두리가 회색빛 파랑 2px로 또렷하고, **왼쪽 12px 색 띠**가 상태별로
      (대기 회색 / 투표중 청록 / 마감 네이비) 보이는지. 15개 카드가 서로 떨어져 보이는지.
- [ ] 배지가 진한 배경 + 흰 글자인지. **흑백으로 찍었을 때 '대기'가 나머지 둘과 갈리는지.**
      (투표중↔마감은 명도가 비슷해 색상 + 좌측 띠 + 도트 깜빡임으로 구분한다.)
- [ ] '투표중' 조의 도트가 깜빡이는지(OS '동작 줄이기' 설정 시 안 깜빡일 수 있음 — 그 경우
      배지 명도 차이로 구분되면 정상).
- [ ] 출석 표기가 '현재/전체' 한 항목만 보이는지(11px 글자가 남아 있으면 회귀).
      **→ §4 때문에 1080p에서는 아예 안 보일 수 있다. 그건 알려진 문제다.**
- [ ] 상태 배지 글자('투표중')가 위아래로 잘려 보이지 않는지.
- [ ] 출석 데이터가 아직 없는 조(체크인 전)에서 레이아웃이 멀쩡한지.

### /hq 회차별 보기 (US-013, `?ops=1` 전용)
- [ ] 분과 필터 아래에 `회차 보기 · 현재 · 1차 · 2차 …` 칩 행이 보이고 기본 선택이 **'현재'**인지.

- [ ] '2차'를 눌렀을 때 (a) 파란 안내 문구("카드가 2차 투표 기준으로 표시되고 있습니다…")가 뜨고,
      (b) 2차를 한 조 카드에 그 조의 **2차** 표수가 뜨는지(현재 라운드 숫자가 아니라).
- [ ] **★ 2차를 하지 않은 조가 `0/12`가 아니라 주황 '미실시' 배지 + 주황 점선 테두리 + 숫자 `—`인지.**
      `0/N`으로 나오면 즉시 보고 — '미실시'와 '0표'가 섞이면 본부가 진행 상황을 오판한다(AC #4의 본체).
- [ ] 같은 화면에 `대기`(회색 배지) 조와 `미실시`(주황 점선) 조가 함께 있을 때 한눈에 갈리는지.
- [ ] 2차가 **진행 중**인 조를 '2차' 보기로 켜 둔 채 그 조에서 표를 더 넣었을 때 30초 안에 숫자가
      올라가는지. **얼어붙어 있으면 보고** — 지연 조회 deps에서 전역 갱신 시각이 빠진 것이다.

- [ ] 와이파이를 끈 채 회차를 바꾸면 주황 배너("N차 표수를 불러오지 못했습니다") + '지금 다시 시도'가

### 투표 결과 이미지 (US-014 — 순수 로직만, 화면 배선은 US-015)

US-014는 SVG 문자열을 만드는 순수 함수뿐이라 이 story 자체에는 육안 확인 대상이 없다.
아래 항목은 **US-015가 PNG 저장 버튼을 붙인 뒤** 실제 파일을 열어서 확인한다.

- [ ] 저장한 이미지에서 **한글이 □로 깨지지 않는지**(SVG 안에 시스템 폰트 스택만 쓴다 —
      웹폰트를 참조하면 SVG-in-Image에서 글자가 통째로 사라진다).
- [ ] 조 이름·제목이 캔버스 밖으로 나가지 않고 필요하면 `…`로 줄어 있는지.
      SVG `<text>`는 줄바꿈이 없어 폭 추정으로만 막고 있다 — 추정이 빗나가면 여기서 드러난다.
- [ ] 막대가 회색 트랙을 **넘지 않는지**. 넘으면 회귀다.
- [ ] 0표 라운드를 저장하면 막대 없이 **'표 없음'**이 나오는지(0% 막대가 그려지면 회귀 —
      '전원 기권'으로 읽힌다).
- [ ] 알려진 동작(버그 아님): **CHECKBOX(복수 선택) 라운드는 비율 합이 100%를 넘는다.**
      `tallyVotes`의 `total`은 투표한 사람 수이고 선택지 카운트는 선택마다 오르기 때문이다.
      숫자는 사실대로 적고 막대 길이만 트랙 안으로 클램프한다 — 회귀로 보고하지 말 것.
- [ ] 회차가 없는(=`0차`가 될 수 있는) 라운드를 저장했을 때 머리글에 **'0차 투표'가 찍히지 않는지**.
- [ ] **저장을 눌렀는데 이미지가 아예 안 나오는 경우** — 글자가 이상한 게 아니라 파일 자체가
      비었거나 안 생기면 SVG 파싱 실패다. `Image.onerror`는 예외를 던지지 않아 조용히 끝난다.
      화면 문구보다 먼저 `result-image.ts`의 출력을 의심할 것.
      (SVG well-formedness는 US-014에서 `xml.etree.ElementTree`로 3종 파싱 확인했다 —
      이스케이프 다발·선택지 10개·0표. 그래도 이 증상이 나오면 새 입력이 그 3종을 벗어난 것이다.)

### 결과 이미지 저장 (US-015 — /mod, 위 US-014 항목과 함께 확인)

- [ ] `/mod` 결과 화면에서 **'이미지 저장'을 눌러 PNG가 실제로 내려받아지는지**.
      파일명이 `<조이름>_<회차>차_<YYYYMMDD-HHmm>.png` 형식인지(예: `1분과_1조_2차_20260829-1432.png`).
- [ ] **파일명에 회차 조각이 빠져 있으면 보고할 것** — 저장은 됐지만 `fetchTeamRounds` 조회가
      실패해 회차를 모르는 상태다(회차 0 = 생략이 의도된 폴백이다).
- [ ] 저장된 이미지가 **흐릿하지 않은지**(2배 배율로 그린다). 흐리면 scale이 1로 떨어진 것이다.
- [ ] **그림이 통째로 비어(흰 사각형) 나오면 즉시 보고** — SVG 루트에서 픽셀 width/height가
      빠져 canvas가 0x0이 된 증상이다(`svgPixelSize`가 null을 돌려주면 저장 자체가 실패해야 정상).
- [ ] 지난 투표 다시보기 오버레이에도 '이미지 저장'이 **'닫기' 위에** 있는지.
- [ ] 다시보기에서 표를 **불러오는 중이거나 실패한 상태에서는 저장 버튼이 아예 안 보이는지**.
      보이면 회귀다 — 그 상태로 저장하면 '표 없음'이라 적힌 가짜 기록물이 남는다.
- [ ] 저장이 실패하는 환경(사파리 사생활 보호 모드 등)에서 버튼 아래 **주황 안내 문구**가 뜨고
      화면이 멈추지 않는지. **'저장 중…'에서 버튼이 계속 비활성인 채 멈춰 있으면 보고** —
      10초 로드 타임아웃이 있어 늦어도 10초 뒤에는 문구가 떠야 한다.
- [ ] 결과 화면에서 **'다시 열기 (60초)'가 저장 버튼보다 위**에 있는지(되돌리기가 시간에 쫓긴다).
- [ ] 알려진 동작(회귀 아님): **풀스크린 결과 송출 화면에는 저장 버튼이 없다.**
      AC가 결과 화면과 다시보기 두 곳만 지목했고, 송출 중 화면에 조작 UI를 늘리지 않기 위해서다.

### 전수 결과 ZIP 내려받기 (US-016 — `/hq?ops=1`)

ZIP 형식 자체는 python `zipfile`로 저장소 밖에서 확인했다(`testzip()` 통과, 한글 이름 보존,
바이트 동일). **다만 그때 담은 것은 합성 바이트이지 진짜 PNG가 아니다** — 아래 (c) 항목이
"진짜 PNG 45장이 실제로 살아 돌아오는가"를 확인하는 유일한 수단이다.

- [ ] 분과 필터·회차 칩 아래에 **'전체 결과 내려받기'** 버튼과 안내 문구
      ("조별 폴더에 회차별 PNG N장이 담깁니다.")가 보이는지.
- [ ] 투표가 하나도 없는 상태에서 버튼이 **회색으로 비활성**이고
      "아직 진행된 투표가 없어 내려받을 결과가 없습니다."가 뜨는지.
      **버튼이 아예 안 보이면 회귀다** — AC는 숨김이 아니라 비활성 + 이유를 요구한다.
- [ ] 누르면 문구가 '표를 불러오는 중…' → **'이미지 만드는 중 n/total'**로 바뀌고 숫자가 올라가며
      **마지막이 45/45(총 장수)에 닿는지**. 진행 중 버튼이 비활성이고, 연타해도 두 번 시작되지 않는지.
- [ ] ★ **내려받은 zip을 실제로 열 것.**
      (a) 조별 폴더(`1분과 1조/`)로 갈려 있고 **한글 폴더·파일명이 깨지지 않는지**
      (Windows 탐색기와 macOS 양쪽에서 — CP437로 읽히면 여기서 깨진다),
      (b) 파일명이 `2차_<제목>.png` 형식이고 장수가 조·회차 수와 맞는지,
      (c) 아무 PNG나 열어 위 US-014/US-015 항목(한글 □ 없음 · 긴 제목이 …로 줄었는지 ·
      막대가 트랙을 안 넘는지 · 2배 배율이라 흐릿하지 않은지)을 확인.
- [ ] zip 파일명이 `조별_투표결과_YYYYMMDD-HHmm.zip`이고, 두 번 받아도 서로 덮어쓰지 않는지.
- [ ] 어떤 조의 표가 화면 숫자보다 **적게** 나오면 즉시 보고 — 표 조회가 잘린 것이다.
      (라운드 10개씩 나눠 받아 막아 뒀다. 조·회차가 더 늘면 다시 볼 지점이다.)
- [ ] 45장 규모에서 **몇 분이 걸리는지 실측**. 이미지는 순차로 만들어진다.
- [ ] 실패 시 버튼 아래 주황 배너("결과를 내려받지 못했습니다. 연결을 확인한 뒤 다시 눌러 주세요.")가
      뜨고 화면이 멈추지 않는지. 일부만 실패하면 zip은 그대로 나오고
      "N장을 내려받았습니다. M장은 만들지 못했습니다."가 뜨는지.
- [ ] 알려진 동작(판단, 뒤집을 수 있음): **아직 투표하지 않은(pending) 라운드도 '표 없음' 한 장으로
      들어간다.** '전수'의 뜻을 따랐다 — 원치 않으면 알려줄 것(필터 한 줄로 뺄 수 있다).

## 6. 브랜치 범위 경고

이 브랜치는 **더 이상 프론트엔드 전용이 아니다.** US-001~008의 모든 커밋은 프론트엔드
파일만 건드렸지만, 작업 중 다른 프로세스/사람이 다음 커밋들을 같은 브랜치에 올렸다:

- `847148b feat(db): 조 테이블 번호 컬럼 + 본부 전용 수정 RPC`
  (`supabase/migrations/20260726_team_table_no.sql`, 70줄)
- `4a288ab feat(attendance): 조 접속코드만으로 출석부 개방 (출석 PIN 2단 제거)`

**주의점**: `847148b`는 `hq_teams()`를 drop 후 재생성하며 **반환 타입을 바꿨다**(`table_no` 추가).
`/hq`가 이 RPC를 쓴다. 그런데 `npm.cmd run check`는 이 변경을 **검증하지 못한다** —
`src/lib/mod-console.ts`의 `HqTeam` 타입은 DB에서 생성된 것이 아니라 손으로 유지하는
타입이라 타입체커가 시그니처 불일치를 볼 수 없다. 0 errors는 여기에 대해 아무 말도 하지 않는다.

→ 배포 시 마이그레이션 적용 순서를 확인하고, `/hq`가 조 목록을 못 불러오는 증상이 나오면
**US-001~006 변경이 아니라 이 마이그레이션부터 의심할 것.**
(US-017이 프론트 쪽 `HqTeam` 타입에 `table_no`를 배선하는 story로 아직 남아 있다.)
