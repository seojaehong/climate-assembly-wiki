# 9/12~13 경주 합숙 운영 코드리뷰

- 검토일: 2026-09-05
- 검토 대상: `ralph/submission-resilience-0912` (`9ac5c9a`)
- 비교 기준: 9/12 준비 기능과 연관된 코드·마이그레이션·운영 자동화
- 현재 배포 확인: `https://climate-assembly.org/deployment-revision.json`의 `sourceCommit`은 `0c8fb33`; 대상 커밋 `9ac5c9a`는 해당 `origin/main`의 조상
- 변경 제한: 제품 코드·DB·운영 상태는 수정하지 않음

## 결론

초안 보존, 오프라인 재전송, 저장 상태 표시, 마감 안내, ZIP 내려받기, 야간 스냅샷 연장은 방향이 좋다. 다만 현재 상태는 **행사 투입 보류**가 맞다. 순차 개통한 다음 꼭지가 기존 조 화면에 자동 반영되지 않고, 마이그레이션 주석이 지시하는 현장 개통 파일도 실제 작업공간에 없다. 아래 차단 이슈를 먼저 닫은 뒤 실제 브라우저와 검증 DB로 드레스 리허설을 해야 한다.

## Findings

### [P0] 순차 개통한 다음 꼭지가 접속 중인 조 화면에 나타나지 않는다

- `supabase/migrations/20260902_s20_open_0912_topics.sql:34-46`은 여섯 꼭지를 `draft`로 심고 행사 중 하나씩 `open`으로 전환하도록 설계한다.
- 그러나 `src/islands/mod/SubmissionPanel.tsx:1535-1552`는 `topicList(code)`를 최초 마운트 때 한 번만 호출한다. 이후 폴링, Realtime 구독, `visibilitychange` 재조회가 없다.
- 수동 새로고침 버튼은 `topics.length === 0`인 준비 화면에만 있다(`SubmissionPanel.tsx:1604-1618`). 첫 꼭지가 이미 열린 뒤 둘째 꼭지가 열리면 기존 탭에는 둘째 꼭지를 불러올 UI가 없다.
- 영향: 현장에서 본부가 꼭지 ②~⑥을 열어도 조별 입력 화면이 그대로여서 전체 페이지 새로고침 안내가 필요하다. 미저장 글이 있으면 운영자와 참가자가 새로고침을 회피할 가능성도 있다.
- 권고: 주제 목록을 주기적으로 재조회하거나 Realtime으로 갱신하되, 기존 `TopicSection`의 로컬 초안 상태를 유지하는 통합 테스트를 추가한다. “주제 1 입력 중 → 서버에서 주제 2 open → 새로고침 없이 주제 2 등장 → 주제 1 미저장 글 유지”를 현장 승인 기준으로 둔다.

### [P0] 현장 개통 절차가 존재하지 않는 파일을 가리킨다

- `supabase/migrations/20260902_s20_open_0912_topics.sql:5-6,38,58-59`은 `10_작업산출물/2026-09-12_0912_개통/0912_개통_세션조.sql`과 `꼭지_열기.sql`을 선행·당일 실행 파일로 지시한다.
- 저장소와 상위 작업공간을 검색했지만 `2026-09-12_0912_개통` 폴더와 두 파일은 존재하지 않는다.
- 세션·조 SQL은 `node scripts/seed-0829-teams.mjs --print-seed-sql`로 생성할 수 있으나, 운영자가 찾을 정본 파일과 꼭지별 open/close SQL은 없다.
- 영향: s20 적용 전 선행 조건을 충족할 정본이 없고, 행사 중 꼭지를 여는 명령도 즉석 작성해야 한다. 잘못된 세션 또는 여러 꼭지를 한꺼번에 여는 운영 사고로 이어질 수 있다.
- 권고: 감사 가능한 단일 운영 패킷을 만든다. 세션·15개 조 생성, 여섯 꼭지 심기, 꼭지별 open/close, 현재 상태 읽기, 롤백, 실행 전후 검증을 순서대로 묶고 각 단계에 예상 행 수와 세션 slug를 고정한다.

### [P1] 기본 live 시드 경로는 테넌시 상속 규칙을 지키지 않는다

- `scripts/session-rosters.mjs:21-28`은 현재 DB에서 새 세션이 기존 세션의 `org_id`·`assembly_id`를 상속해야 한다고 명시한다.
- `--print-seed-sql` 경로는 이를 반영하지만, 인자 없이 실행되는 `runLive()`는 `scripts/seed-0829-teams.mjs:80-83`에서 `slug`, `title`, `config`, `status`만 insert한다.
- 영향: NOT NULL 전환이 적용된 운영 DB에서는 새 세션 생성이 실패한다. 제약이 느슨한 환경에서는 `org_id`가 비어 멀티테넌시 불변식을 깨뜨릴 수 있다.
- 권고: 기본 live 경로를 제거하고 검증된 SQL 패킷만 쓰거나, live 경로도 같은 상속·원자 트랜잭션·사후 검증을 사용하도록 통합한다. 두 경로의 결과가 동일하다는 테스트가 필요하다.

### [P1] 오프라인 재전송의 충돌 검사가 원자적이지 않아 마지막 저장이 다른 입력을 덮을 수 있다

- 재전송은 `SubmissionPanel.tsx:539-544`에서 서버 `updated_at`을 읽은 뒤 별도 요청으로 `submissionSave()`를 호출한다.
- 현재 RPC는 `p_base_updated_at` 또는 revision을 받지 않고 전체 항목을 교체한다(`supabase/migrations/20260830_s15_submission_server_line_split.sql:119-173`; 원형은 `20260808_s1_assembly_topic_submission.sql:188-225`).
- GET과 SAVE 사이에 같은 조의 다른 탭·기기가 저장하면 검사 직후의 새 내용을 큐의 옛 내용이 덮을 수 있다. 수동 저장끼리도 같은 문제가 있다.
- 권고: 저장 RPC 안에서 `updated_at` 또는 증가 revision을 비교하는 낙관적 잠금(서버가 기준 버전을 확인하고 충돌을 반환하는 방식)을 구현한다. DB 변경이므로 적용 전 별도 승인이 필요하다.

### [P1] 날짜+순번 접속코드는 공개 RPC의 쓰기 권한으로 쓰기에는 예측 가능하다

- `src/lib/deliberation.ts:4-7`은 `join_code`를 조 운영 RPC의 capability(코드를 가진 사람이 권한을 갖는 방식)로 사용한다고 명시한다.
- `scripts/session-rosters.mjs:6-10,62-80`은 코드를 `091201`부터 `091215`까지 결정적으로 만든다.
- 영향: 행사 날짜와 조 수를 아는 외부인이 모든 조 코드를 쉽게 추측해 제출물을 읽거나 덮어쓸 수 있다. 최종 제출 전에는 특히 취약하다.
- 권고: 인쇄 편의용 짧은 코드와 서버 쓰기 capability를 분리한다. 짧은 코드는 1회 교환용으로만 쓰고, 이후 세션·조에 묶인 만료 토큰을 발급한다. 당장 구조 변경이 어렵다면 행사 네트워크·접근 경로 제한, 코드 회수 계획, 감사로그 감시를 임시 통제로 둔다.

### [P2] 본부 마감 RPC가 토큰의 조직·세션 범위를 확인하지 않는다

- `supabase/migrations/20260901_s17_topic_deadline.sql:77-95`은 토큰의 `scope = 'hq'`만 확인하고 전달된 `p_topic_id`를 곧바로 갱신한다.
- 영향: 한 조직의 HQ 토큰이 다른 세션·조직의 topic UUID를 알면 마감을 바꿀 수 있다. 현재 단일 행사에서는 노출이 낮지만 SaaS 멀티테넌시 방향과 충돌한다.
- 권고: 토큰에서 파생한 `org_id`·허용 세션과 topic의 `org_id`·session_id를 서버에서 일치시키고, legacy null-org 토큰의 허용 범위를 명시적으로 제한한다.

## 긍정적으로 확인한 부분

- 초안을 `localStorage → sessionStorage → memory` 순으로 보존하고 저장 성공 시 모든 계층의 낡은 초안을 제거하는 설계는 데이터 유실 방지 목적에 맞다.
- 네트워크 실패만 큐에 적재하고, 영구 실패는 재시도하지 않으며, 충돌 시 자동 덮어쓰기를 멈추는 UX는 현장 복구성에 도움이 된다.
- 마감은 안내와 잠금을 분리해 마감 뒤에도 저장 가능하게 한 판단이 적절하다.
- 9/12 밤부터 9/13 아침까지 스냅샷 공백을 없앤 일정 계산과 테스트가 있다.
- 세션 slug 기본 인자를 제거하고 호출부에서 명시하도록 한 변경은 이전 회차 데이터 오조작 위험을 줄인다.
