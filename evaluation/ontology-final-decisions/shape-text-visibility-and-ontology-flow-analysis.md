# 최종결정 온톨로지 도형/가시성/연결 구조 재진단

## 진단 요약

현재 화면의 가장 큰 문제는 글자 크기만이 아니라, 최종결정이 원자료와 숙의 과정에서 도출된 것처럼 보이지 않고 별도로 편집된 결과물처럼 보인다는 점이다. 생성 데이터에는 원자료, 전사, 통합 그래프, 투표, 최종 결론을 잇는 과정 그래프가 포함되어 있지만, 시각화 화면에서는 이 흐름이 하나의 이야기 경로로 드러나지 않는다.

발표용 화면은 “무엇이 최종 결론인가”보다 먼저 “어떤 숙의 과정을 통해 이 결론으로 왔는가”를 보여줘야 한다. 지금 구조는 최종 노드와 근거 노드가 한 화면에 섞여 배치되기 때문에, 사용자가 말한 “숙의과정을 통해 - 무슨 말? - 진행 - 결론”의 중간 단계가 잘려 보인다.

## 도형 모형 문제

현재 도형은 주로 노드의 종류를 구분한다. 예를 들어 최종결정, 조항, 합성 노드 같은 속성에 따라 모양이 달라진다. 이 방식은 데이터 타입을 구분하는 데는 유용하지만, 발표자가 보여주려는 “도출 과정”을 설명하기에는 부족하다.

특히 최종결정 노드가 합성 노드의 시각 규칙과 겹치면, 청중에게 “논의에서 자연스럽게 도출된 결론”이 아니라 “나중에 사람이 재구성한 카드”처럼 보일 수 있다. 이것이 사용자가 느낀 임의 편집감의 핵심이다.

개선 방향은 노드 종류 중심 도형이 아니라 과정 단계 중심 도형이다.

- 원자료/전사: 문서 또는 기록 형태
- 발언/질문: 말풍선 또는 발화 형태
- 쟁점화: 질문 또는 쟁점 허브
- 숙의 진행: 비교, 통합, 압축을 나타내는 연결/브리지
- 투표/발표 근거: 선택 또는 확인 근거
- 최종 결론: 결론 배지 또는 확정 노드
- 미확인/부분 반영: 경고 또는 검토 필요 노드

이렇게 바꾸면 도형 자체가 “데이터 타입”이 아니라 “숙의 과정의 위치”를 설명하게 된다.

## 텍스트 가시성 문제

텍스트는 이미 더 크게 보이도록 조정되었지만, 발표용으로는 큰 글자만으로 충분하지 않다. 노드 수가 많은 그래프에서 모든 라벨을 동시에 크게 보여주면, 글자가 서로 밀리고 연결선 의미가 약해진다.

발표 첫 화면은 전체 그래프가 아니라 과정 요약 화면이어야 한다. 예를 들어 원자료에서 최종 결론까지 이어지는 대표 경로를 먼저 보여주고, 각 결론을 클릭했을 때 세부 근거 노드가 펼쳐져야 한다.

따라서 가시성 개선의 우선순위는 다음과 같다.

- 첫 화면에서는 큰 글자와 적은 노드로 과정 흐름을 보여준다.
- 세부 근거는 클릭 또는 모드 전환으로 펼친다.
- 최종결정 화면에서는 모든 근거를 한 번에 보여주기보다 대표 근거와 미확인 지점을 구분한다.
- 발표용 기본값은 전체 네트워크가 아니라 “스토리 모드”가 되어야 한다.

## 온톨로지 연결 문제

현재 생성 스크립트에는 과정 그래프가 존재한다. 원자료에서 전사, 통합 그래프, 최종 투표, 최종 결론으로 이어지는 데이터 구조가 있다. 그러나 화면에서는 이 구조가 좌에서 우로 흐르는 도출 경로로 배치되지 않고, 일반 네트워크처럼 펼쳐진다.

또한 관계 이름이 “연결”, “압축”, “확정”, “지지”처럼 넓은 의미로 표현되어 있어, 청중이 각 연결의 역할을 즉시 이해하기 어렵다. 사용자가 말한 “무슨 말?”에 해당하는 중간 노드, 즉 발언이 어떤 쟁점으로 번역되었는지 보여주는 단계가 필요하다.

권장하는 관계 구조는 다음과 같다.

- 논의에서 제기됨
- 쟁점으로 정리됨
- 숙의에서 비교됨
- 숙의에서 통합됨
- 투표로 압축됨
- 최종 결론으로 확정됨
- 미확인 또는 부분 반영

이 관계들이 보이면 최종결정은 편집된 문장이 아니라, 원자료와 숙의를 통과한 결과로 보인다.

## 권장 화면 구조

새 기본 화면은 다음의 층위형 구조가 적합하다.

원자료/전사 -> 발언/질문 -> 쟁점 -> 숙의 진행 -> 투표/발표 근거 -> 최종 결론

이 구조에서는 “무슨 말?”이 별도 중간 노드로 살아 있어야 한다. 예를 들어 어떤 발언 묶음이 “교육을 별도 의제로 둘 것인가, 다른 의제에 통합할 것인가” 같은 쟁점 노드로 정리되고, 그 쟁점이 숙의와 투표를 거쳐 최종 의제에 연결되는 식이다.

운영규정과 의제는 각각 별도 최종결정 세트를 유지하되, 발표 화면에서는 둘을 바로 결과물로 보여주기보다 “과정에서 결론으로 가는 지도” 위에 올려야 한다.

## 다음 구현 제안

기존 최종결정 JSON은 유지하고, 별도 발표용 스토리 온톨로지 뷰를 추가하는 편이 안전하다. 기존 데이터를 덮어쓰지 않고, 현재 생성 스크립트의 과정 그래프를 기반으로 발표용 계층 레이아웃을 만든다.

구현 단위는 다음이 적합하다.

- `final-process-to-conclusion-0704.json`을 기본 발표 데이터로 승격
- 좌우 단계형 레이아웃 추가
- 관계 라벨을 과정 의미 중심으로 재명명
- 최종결정 노드 클릭 시 운영규정/의제별 근거 트레일 표시
- 부분 반영 또는 미확인 자료는 별도 검토 레일로 표시

이렇게 하면 “우리가 임의로 편집한 결론”이 아니라 “온톨로지 기준으로 숙의 과정에서 결론이 생성되는 장면”을 보여줄 수 있다.

## 첫 번째 결정 질문

발표 첫 화면은 어느 쪽이어야 하는가?

추천 답: “전체 도출과정 스토리”를 첫 화면으로 두고, 각 최종 결론을 누르면 운영규정/의제별 근거 트레일이 펼쳐지는 방식이 좋다. 발표에서는 먼저 신뢰 가능한 도출 경로를 보여준 뒤, 필요할 때 세부 근거를 열어보는 흐름이 더 설득력 있다.
