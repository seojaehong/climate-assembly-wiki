## 정본 양식 확인

- 정본: `10_작업산출물/2026-09-12_회의자료_수신원본/10_중복정리본/정책권고안 표(양식)_최종.hwpx`
- ObjectFinder 전수 추출로 `권고번호`, `권고 제목`, `배경·문제 인식`, `권고 내용`, `기대 효과`, `이행 일정`, `핵심원칙(권고수준)`, `기타의견`, `분과 투표 결과`를 확인했다.
- 오늘·내일 화면은 `권고 제목`, `배경·문제 인식`, `권고 내용`만 활성 입력·제출 검증 대상으로 삼는다.
- 기존 기대 효과는 데이터와 개정 이력에 보존하되 이번 화면에서 필수로 요구하지 않는다. 이행 일정 이후 필드도 이번 단계에서 입력을 요구하거나 표시하지 않는다.

## 구현 범위

- 구조를 `분과 → 동적으로 추가 가능한 의제 → 의제별 복수 권고안`으로 구현했다.
- 1·2·3분과 초기 의제 25건은 `9·8·8`로 유지하며, 현장에서 의제와 권고안을 추가할 수 있다.
- 전체 15개 조를 여러 의제에 배정할 수 있도록 했고, 배정·재배정은 HQ가 수행한다.
- 진행상태는 의제가 아니라 권고안마다 `대기 → 논의 중 → 초안 작성 → 조 확인 → 제출 완료`의 5단계로 관리한다.
- HQ는 로그인 직후 전체 3개 분과를 보며, 분과별 필터와 독립 송출 화면을 사용할 수 있다.
- 기록모더레이터는 자기 조에 배정된 의제를 드롭다운에서 선택하고, 같은 의제에 권고안을 여러 개 작성한다. 자기 분과에서 새 의제를 추가하면 자기 조에 자동 배정된다.
- HQ와 기록모더레이터 모두 삭제 대신 보관을 사용하며, 권고안 문안과 상태 변경은 행위자·시각·요청 ID를 포함한 append-only 이력으로 남는다.
- 기존 제출·출석·투표·8/29 기록 구조는 변경하지 않고, 기존 s23 위에 additive s24 테이블과 v2 RPC만 추가했다.

## 운영 반영

- 기명 HQ 계정 3건을 담당 분과와 함께 활성화했다.
- 초기 자격증명은 운영 DB에 bcrypt 해시로만 저장했으며 코드·Git·로그·Notion에는 평문을 남기지 않았다.
- 신규 s23·s24 마이그레이션을 운영 DB에 적용했다. PostgreSQL 16 임시 DB에서 s23 위 통합 적용과 재적용을 먼저 검증했고, 운영에서는 실제 세션 slug를 기준으로 신규 테이블 5개, RPC 오버로드, 9·8·8 의제, 15개 조, 열린 작업단계 1개를 읽기 전용으로 재검증했다.
- 저장된 세 기명 HQ 계정은 모두 활성 상태이며 담당 분과가 각각 1·2·3분과로 연결되어 있다. 비밀번호 저장값은 평문이 아니고 해시가 존재함을 확인했다.
- 수신 원본 13건과 중복 정리본 12건은 프로젝트 작업산출물 폴더에 보관했다.
- PR #40을 병합해 Cloudflare 운영 배포를 완료했다. 운영 `/hq`에서 세 기명 HQ 계정 모두 실제 로그인되며 로그인 행위자 이름, 전체 25개 의제, 분과별 9·8·8 필터, 분과 송출 화면을 확인했다.

## 설계상 보호장치

- 요청 UUID를 재사용해 네트워크 재시도 시 의제·권고안·상태 이력이 중복 생성되지 않는다.
- 권고안 개정은 최신 revision version을 비교해 오래된 화면의 덮어쓰기를 거부하고, 개정과 상태 갱신은 동일 권고안의 동시 쓰기를 직렬화한다.
- 요청을 시작한 작업단계 ID를 재시도 데이터에 고정하며, 열린 단계가 하나가 아니면 화면과 RPC가 모두 쓰기를 차단한다.
- 조 세션은 자기 분과와 자기 조 범위에서만 의제·권고안을 기록할 수 있고, HQ는 세 분과 전체를 운영한다.
- 수정·삭제·truncate 방지 트리거와 보관 이벤트로 기존 기록을 덮어쓰지 않는다.
- 브라우저 오프라인 상태에서도 초안을 로컬에 남기고 재접속 후 전송할 수 있다.

## 검증 환경 참고

- 기존 CLI 로딩 오류는 Node 24 문제가 아니라 Windows CRLF shebang 변환 문제였다. LF 고정 후 해당 22개 테스트가 통과했다. 원격 Node 20 전체 루트 검사 128개 파일 통과를 확인했다.
- PostgreSQL 전체 드라이런은 임시 컨테이너 내부의 0600 seed 파일로 보완해 166초 만에 통과했다. 운영 DB 연결·변경은 0건이다.
- 로컬 개발 서버의 HMR 연결과 Codex 경로 별칭에 영향을 받는 검사 결과는 운영 빌드 CI와 구분한다. 전체 마감 판정·후속 정정은 `completion-audit-20260912.md` 및 `report.json`을 따른다.
- 운영 DB에서 테스트 전용 검증 SQL은 고정된 합성 세션 UUID를 전제로 하므로 실제 운영 세션 UUID와 맞지 않았다. 따라서 운영에서는 UUID를 가정하지 않고 `0912-deliberation` slug로 대상 세션을 찾는 읽기 전용 검증을 사용했다.

## 현장 사용 순서

1. HQ에서 본인 이름으로 로그인한다. 기본 화면은 세 분과 전체이며 담당 분과는 접근 제한이 아니다.
2. 분과·주제를 선택하고 배정할 조를 체크한다. 여러 조 배정과 재배정이 가능하다. 실제 배정은 현장 책임자가 결정하며 점검용 배정은 모두 원복했다.
3. 기록모더는 자기 조로 접속해 배정된 주제 아래 권고 제목·배경과 문제 인식·권고 내용을 작성한다. 카드 상단의 다음 행동으로 5단계를 진행한다.
4. HQ는 상태 요약을 눌러 필터링하고 다시 누르면 해제한다. 분과 송출 또는 개별 주제 송출을 연다. 원문과 현재 공유문안은 주제 화면에서 확인한다.
5. 저장 실패 시 미전송 안내를 확인하고 같은 내용으로 재시도한다. 서버 저장 완료 여부가 불명확하다고 새 권고안을 중복 생성하지 않는다.
6. 기존 기록 검토가 필요할 때만 인증 후 `/hq?ops=1&view=submissions`를 사용한다. 일반 접속 화면에는 이전 산출물 탭을 노출하지 않는다.

멀티보팅·사진 업로드·A/B/C/D 통합지원은 이번 긴급 범위에 포함하지 않는다. 실제 행사 기기의 빔 연결·현장 네트워크 점검은 운영자가 현장에서 확인해야 한다.
