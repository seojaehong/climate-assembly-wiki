## 1. 최종 판단

현재 구현은 동시편집, 오프라인 복구, 충돌 방지, 권한 통제, 명단·라이브 개통 차단 장치 등 **기술적 안전성은 유지**되고 있다. 그러나 새로 받은 ADR 수정본의 실제 숙의 순서와 시스템에 심어진 9/12~13 주제·시간·산출물 정의가 일치하지 않는다.

따라서 현재 상태는 다음과 같이 판정한다.

| 영역 | 판정 | 근거 |
|---|---|---|
| 기본 기능 안정성 | 유지 | 기존 자동 검증과 로컬 회귀 검증 통과 |
| 확정 계획 의미 정합성 | 개통 차단 | 시스템은 과거의 이해관계자 발언·교차검토·분과 의결 흐름을 안내 |

## 3. 개통 차단 발견사항

### 3.1 시스템에 심어진 6개 주제가 과거 계획을 그대로 따른다

`supabase/migrations/20260902_s20_open_0912_topics.sql`은 과거 운영안인 `2026-06-18_운영_세부계획_v2.md`를 근거로 삼고 있다.

- 이해관계자 발언 청취, 분과 간 교차검토, 3분의 2 의결을 전제로 한 시간·안내문 포함

새 자료에는 해당 절차가 없고, 대신 배경·문제점 → 기대효과 → 권고문 → 세부 정책제안 → 도슨트 검토 → 중복 표시·대표 제목 순으로 진행한다. 이 마이그레이션을 그대로 적용하면 화면은 안정적으로 작동하더라도 참가자에게 틀린 순서와 틀린 산출물을 안내한다.

동일한 과거 정의가 `supabase/verify/20260902_s20_open_0912_topics.sql` 37~52행과 94~108행에도 고정되어 있어, 현재 검증은 잘못된 주제를 오히려 정답으로 보호한다.

**필요 조치:** 라이브 DB 적용 여부와 기존 제출 존재 여부를 읽기 전용으로 확인한 뒤 처리 방식을 정한다.

- 기존 제출 존재: 순번이나 의미를 조용히 바꾸지 않고 새 세션 매핑 또는 보존·이관 절차 적용

DB 스키마나 라이브 데이터 변경은 별도 승인 전에는 실행하지 않는다.

- `09:10-09:10 (10')`와 상세표의 `09:00~09:10`, 1분과 강의 종료 12:40과 공통 중식 시작 12:30 등 내부 시간 충돌 존재
- 장소표에서 메인 회의장은 분과1로 쓰면서 중강의실 A·B도 분과1·2로 적어 분과1이 중복되고 분과3이 누락됨

**필요 조치:** 원본 작성자에게 위 항목을 반영한 배포용 정본을 다시 받고, 새 파일의 해시를 계획 계약에 등록한다. 과거 일정표 이미지는 교체하거나 단순 예시임을 명시해야 한다.

## 4. 높은 우선순위 발견사항

### 4.1 디지털 도구의 정본 역할이 아직 결정되지 않았다

새 계획은 권고 하나를 범주, 배경·문제점, 기대효과, 권고문, 복수 정책제안, 일정, 5개 원칙 검토, 기타·반대 의견, 중복 유형, 대표 제목까지 이어서 추적해야 한다.

현재 구조는 다음 한계가 있다.

- `supabase/migrations/20260808_s1_assembly_topic_submission.sql` 58~81행: 주제·조별 제출 1건과 일반 문장 목록 구조
- `src/islands/mod/SubmissionPanel.tsx` 1267~1332행: 이름과 자유서술 입력 중심
- `src/islands/mod/submission-report.ts` 52~71행, 108~134행: 주제 → 조 → 문장 목록으로 출력

권고 식별자와 단계 간 연결이 없어 디지털 도구를 정본으로 쓰면 한 권고의 완결성을 안정적으로 복원하기 어렵다. 반면 기존 작업정의에는 전달 형태가 콘솔·인쇄·덱 중 미정이라고 남아 있다.

**권고:** 이번 행사에서는 현장 카드를 정본으로 두고 디지털 입력은 단계별 스냅숏·백업으로 사용한다. 디지털 정본으로 전환하려면 먼저 데이터 모델 변경안과 마이그레이션을 승인받아야 한다.

- 3행의 `본문 137행`은 현재 추출본의 실제 136행과 다름
- 25행의 `해당 없음 4`에는 항목이 5개 열거됨

이는 운영 판단을 바꾸는 오류는 아니지만, 후속 변경 추적에서 집계가 어긋나지 않도록 정정하는 것이 좋다.

## 5. 유지해야 할 구현 강점

다음 기능은 새 계획에 맞춰 문구와 데이터만 교정하면 그대로 활용할 가치가 있다.

- 주제 변경 감지와 5초 단위 갱신
- 입력 맥락 보존과 오프라인 큐
- 낙관적 동시성 제어와 충돌 표시
- HQ 개통·중단 통제와 실패 시 닫힘 처리
- 접근성·키보드 흐름 보강
- 이전 주제를 강제로 닫지 않아 단계 재방문 가능
- 토큰 만료가 9/13 야간까지 이어지는 이틀 운영 구조
- 명단·라이브 설정·백업 증거가 없으면 준비 완료로 판정하지 않는 게이트

현재 `evaluation/0912-13-readiness-report.json`도 명단, 라이브 롤아웃, 현장 단말·네트워크, 수동 접근성 점검, 백업·복원이 완료되지 않아 `not_ready`를 유지한다. 이 판정은 올바르다.

## 6. 승인용 디지털 체크포인트 초안

아래 8단계는 확정 자료를 디지털 미러·백업 방식으로 옮긴 **승인 전 작업안**이다. 계획 자체가 디지털 주제 개수를 지정하지 않았으므로 운영 책임자 확인 전에는 DB에 적용하지 않는다.

## 7. 수정·검증·개통 순서

1. **정본 동결**: 시간 충돌, 장소표, 과거 이미지, 미확정 문구를 정리한 배포본 수령 및 해시 등록
2. **도구 역할 승인**: 현장 카드 정본·디지털 미러 방식 또는 디지털 정본 방식 결정
3. **계획 계약 작성**: 개정 식별자, 해시, 공식 시간, 체크포인트, 산출물 상태, 금지 문구를 기계 판독 가능한 파일로 고정
4. **일괄 정합화**: 주제 마이그레이션, SQL 검증, 화면 문구, 공개 세션 문서, 리허설 픽스처, 런북을 같은 계약에서 검증
5. **이틀 리허설**: 9/12 야간 인계 → 9/13 복원 → 최종 백업까지 포함해 현장 단말과 실제 명단으로 검증
6. **승인 후 개통**: DB 상태를 먼저 읽기 전용으로 확인하고, 교정 마이그레이션·라이브 적용·배포는 별도 승인 뒤 수행

개통 조건은 단순 자동검증 통과가 아니라 다음 증거가 모두 있어야 한다.

- 배포용 정본 해시
- 계획 계약과 모든 사용자 노출 문구의 일치
- 확정 명단과 분과·조 매핑
- 현장 단말·네트워크·접근성 점검
- 야간 인계와 백업·복원 실측 기록
- 라이브 DB 적용 전후 검증 및 되돌림 절차
